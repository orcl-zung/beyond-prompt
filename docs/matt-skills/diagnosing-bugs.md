# 诊断与双轴审查

`diagnosing-bugs` 处理根因未知的问题，`code-review` 在实现完成后检查代码是否同时符合仓库标准和原始需求。一个建立故障反馈，一个防止“做对了错误的事”。

## 困难 Bug 的六阶段循环

### 1. 建立 Tight Feedback Loop

先找到一条已经运行过、能准确捕获该症状的命令。它必须：

- Red-capable：真的能在 Bug 存在时失败。
- Deterministic：结果稳定，或显著提高偶发 Bug 复现率。
- Fast：以秒计。
- Agent-runnable：无需人工反复介入。

没有这条循环，不进入理论推理。

### 2. 复现并最小化

逐项删除输入、配置、调用者与数据。剩余每个元素都必须是复现所必需。

### 3. 排列可证伪假设

提出 3 到 5 个带预测的假设。不能产生可观察预测的解释只是直觉。

### 4. 定向 Instrument

一次改变一个变量。优先调试器，其次在能区分假设的边界加入带唯一前缀的临时日志。

### 5. 回归测试与根因修复

在能复现真实 Bug 模式的 Seam 上先写失败测试，再修复。若不存在可信 Seam，应记录这个架构发现。

### 6. 清理与复盘

重新运行原始反馈循环，删除临时 Instrumentation，并在提交中写清根因。若根因暴露错误 Seam 或耦合，再进入架构改进流程。

## `code-review` 的固定点

Review 必须先确定比较基线，例如 `main`、某个 Tag 或 Commit，并使用 merge-base 比较：

```bash
git diff <fixed-point>...HEAD
```

没有固定点，审查范围会漂移。

## 两个独立审查轴

### Standards

改动是否符合仓库记录的编码标准、架构约束和基本 Code Smell 基线。

### Spec

改动是否忠实实现了来源 Issue、PRD 或 Spec，包括验收标准与明确非目标。

两轴由平行、隔离上下文的审查者执行，再并列汇总。这样 Standards 审查不会因为知道产品意图而放宽结构问题，Spec 审查也不会被风格偏好带偏。

## 为什么两者都需要

| 情况 | Standards | Spec | 结论 |
| --- | --- | --- | --- |
| 代码整洁，但遗漏关键需求 | 通过 | 失败 | 不能交付 |
| 功能符合需求，但破坏项目约束 | 失败 | 通过 | 需要修正 |
| 两轴均通过 | 通过 | 通过 | 可进入提交 |

`implement` 在完整测试后自动进入这一步。完成审查和修复后，再提交当前分支。
