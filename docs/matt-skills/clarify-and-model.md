# 对齐与领域语言

Matt Skills 把“需求没说清”和“项目语言不统一”视为同一个连续问题：先通过 `grilling` 找到真实决定，再通过 `domain-modeling` 把决定写成可复用语言。

## `grill-me` 与 `grill-with-docs`

两者共享同一个 `grilling` 原语：

1. 沿设计树一次解决一个问题。
2. 先处理影响后续分支的上游决定。
3. 每个问题给出 Agent 的推荐答案。
4. 等用户反馈后再进入下一题。
5. 能从代码库查到的事实直接探索，不询问用户。

区别在于是否留下项目状态：

| Skill | 使用场景 | 持久产物 |
| --- | --- | --- |
| `grill-me` | 没有代码库的计划或设计 | 无 |
| `grill-with-docs` | 与现有项目相关的变更 | `CONTEXT.md`、必要 ADR |

## 领域语言如何减少上下文成本

没有共同词汇时，Agent 会反复解释一串关系。有了规范术语，讨论、文件名、函数名和测试名可以使用同一个短表达。

```md
# CONTEXT.md

## Materialization

将逻辑课程内容映射到文件系统中稳定位置的过程。

## Materialization cascade

父级路径变化引发后代内容路径连续更新的行为。
```

词汇不只是节省字数，它让 Agent 更容易搜索代码、识别重复概念和避免同义词漂移。

## `domain-modeling` 的主动纪律

- 用户使用模糊词时，提出更精确的规范术语。
- 新说法与现有 `CONTEXT.md` 冲突时立即指出。
- 用具体边界案例压测概念关系。
- 对照代码确认口头模型与现实一致。
- 术语一旦确认，立刻更新词汇表，而不是会后批量回忆。

`CONTEXT.md` 只保存领域概念，不放实现决策、会议草稿或任务清单。

## ADR 的严格门槛

只有决定同时满足以下条件，才值得记录 ADR：

1. 未来很难逆转。
2. 缺少背景会让后来者困惑。
3. 确实比较过有意义的替代方案。

领域词汇进入 `CONTEXT.md`，架构取舍进入 ADR，用户目标进入 Spec。把它们混在一起会让所有文档失去用途。

## 完成信号

- 用户明确确认了关键分支。
- 核心术语只有一个含义。
- 代码与口头描述的冲突已解决。
- 难逆取舍有必要的 ADR。
- 后续 Spec、Ticket、模块和测试能直接使用同一语言。

共同语言建立后，进入[深模块与代码库健康](./deep-modules.md)。
