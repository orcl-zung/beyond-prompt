# 原型与研究支线

主流程中的问题不一定都能靠对话解决。`prototype` 产生运行证据，`research` 产生一手资料证据；两者都为设计决策服务，而不替代设计。

## `prototype`：用一次性代码回答一个问题

原型有两条分支。

### Logic Prototype

验证状态机、业务规则或交互顺序。通常是一个小型终端程序，每次操作后展示完整状态。

### UI Prototype

验证视觉与交互方向。在同一路由提供多个真正不同的方案，允许用户快速切换比较。

## 原型规则

1. 问题先于代码，必须写清想回答什么。
2. 从第一天标记为 throwaway。
3. 一个命令即可运行。
4. 默认只用内存状态。
5. 不做与问题无关的测试、抽象和错误处理。
6. 得到答案后保留结论，删除或吸收代码。

原型不是“低配生产版”，不能稍微清理就上线。

## 用 Handoff 隔离支线

```text
原设计会话
  -> handoff 到原型会话
  -> prototype
  -> 记录问题、证据和结论
  -> handoff 回原设计会话
```

这样原型实现细节不会占满主设计上下文。

## `research`：让后台 Agent 做阅读工作

当问题依赖框架文档、标准、源码或第一方 API 时，`research` 会启动后台 Agent：

1. 只追踪高可信一手来源。
2. 将每个事实链接回拥有该事实的来源。
3. 输出一份带引用的 Markdown 到仓库既有研究目录。
4. 主会话可以继续工作，不必等待全部阅读完成。

Research 的产物应带入 `grill-with-docs`，帮助人做取舍；资料本身不会替团队决定产品方向。

## 选择哪一条

| 问题 | 工具 |
| --- | --- |
| 这个状态模型运行起来是否合理？ | `prototype` |
| 三种 UI 哪一种更易理解？ | `prototype` |
| 当前框架版本支持哪种 API？ | `research` |
| 某个标准对安全边界如何规定？ | `research` |
| 既需规范事实又需体验方案 | 先 `research`，再 `prototype` |

证据回到主流程后，使用 [Implement 与 TDD](./tdd.md) 建立正式实现。
