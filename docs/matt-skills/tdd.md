# Implement 与 TDD

`implement` 是面向用户的实现编排器，`tdd` 是内部复用的反馈纪律。前者规定任务如何收尾，后者保证每个行为切片都有真实信号。

## `implement` 的合同

输入是一份 Spec、一个 Ticket 或一组明确工作。流程要求：

1. 在预先确认的 Seam 上尽可能使用 `tdd`。
2. 开发中定期运行类型检查和单个测试文件。
3. 结束时运行完整测试套件。
4. 使用 `code-review` 审查全部改动。
5. 将结果提交到当前分支。

它不是“开始写代码”的别名，而是从任务到已审查提交的闭环。

## 先确认测试 Seam

Seam 是观察公开行为的位置。写测试前先与用户确认：

```text
公开 Interface 是什么？
哪些 Seam 承载关键行为？
哪些行为值得测试？
```

测试只能放在预先同意的 Seam 上，避免 Agent 在低价值内部细节上堆覆盖率。

## 好测试的三个条件

- **行为导向**：通过公开 Interface 观察结果。
- **独立真值**：期望值来自规格、已知示例或其他独立来源。
- **重构稳定**：内部函数改名或重排不应破坏测试。

需要避免：

- Mock 内部协作者和测试私有方法。
- 用与实现相同算法重新计算预期值，形成 tautological test。
- 先批量写完所有测试，再批量实现。

## Red-Green 纵向循环

```text
选择一个 Seam 上的一个行为
  -> Red：测试因缺少该行为而失败
  -> Green：只写足够代码使它通过
  -> 选择下一个行为
```

每个测试是一个 Tracer Bullet。下一轮测试应根据上一轮真实实现学到的东西产生。

官方当前版本把重构放到 Review 阶段，而不是塞进每次 Red-Green 循环。这样实现反馈保持单一：先证明行为，再统一审查结构。

## 运行节奏

| 时机 | 检查 |
| --- | --- |
| 每个切片 | 当前测试文件 |
| 实现过程中 | 类型检查、相关测试 |
| 全部行为完成 | 完整测试套件 |
| 提交前 | `code-review` 的 Standards 与 Spec 两轴 |

## 何时单独调用 TDD

已有一个具体行为、无需完整 Spec 时，可以直接请求 `tdd`。它适合小功能和明确 Bug 修复，但仍需要确认测试接口和观察有效 Red。

当问题并非已知行为缺失，而是根因不明的异常，应进入[诊断与双轴审查](./diagnosing-bugs.md)。
