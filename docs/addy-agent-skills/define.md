# Define：从想法到规格

Define 阶段不急着回答“怎么实现”，而是先确认“真正要解决什么”。它由 `interview-me`、`idea-refine` 和 `spec-driven-development` 三个 Skills 组成。

## `interview-me`：提取真实意图

适用于需求欠明确，或者用户自己也还在探索的时候。流程强调一次只问一个问题，并为问题附上当前猜测。

```text
当前理解：你更在意减少重复操作，而不是增加自动化选项。
信心：65%
问题：用户一天通常执行这个操作几次？
我的猜测：超过 10 次。
```

这种方式让用户可以同时回答问题和纠正 Agent 的模型。访谈持续到 Agent 对意图达到约 95% 信心，并获得用户明确确认。

需要特别分辨：用户真正想要的结果，与用户认为自己“应该想要”的方案。需求访谈的产物是清晰问题陈述，不是立刻锁定某个实现。

## `idea-refine`：先发散，再收敛

当已有粗略概念，但还需要比较方向时使用。典型过程是：

1. 提取目标、约束与当前假设。
2. 生成多个真正不同的方案，而不是同一方案的轻微变体。
3. 从价值、成本、风险和可逆性比较。
4. 推荐一个方向，并明确不做什么。
5. 列出仍需验证的关键假设。

最终输出应包含 Problem Statement、Recommended Direction、MVP Scope、Not Doing 和 Open Questions。

## `spec-driven-development`：规格先于代码

适用于新项目、新功能、跨模块变更或重要架构决定。官方流程包含四个带人工门禁的阶段：

```text
SPECIFY -> PLAN -> TASKS -> IMPLEMENT
   |         |       |         |
 人工确认   人工确认  人工确认   人工确认
```

### 一份有效规格包含什么

- **Objective**：用户问题、目标和验收条件。
- **Tech Stack**：框架、语言与关键版本。
- **Commands**：构建、测试、Lint 和开发命令。
- **Project Structure**：目录布局及职责。
- **Code Style**：约定和一个可信示例。
- **Testing Strategy**：测试层级、位置和重点。
- **Boundaries**：Always、Ask first、Never。
- **Success Criteria**：具体且可测试的完成标准。
- **Open Questions**：尚未解决的问题。

### 把模糊要求改成成功标准

```text
模糊要求：让仪表盘更快。

成功标准：
- LCP 在目标设备和网络下低于约定阈值。
- 初始数据请求在约定时间内完成。
- 加载过程不产生明显布局偏移。
```

具体阈值必须根据项目基线和用户目标确认，不能由 Agent 随意发明。

## 规格是活文档

实现中发现数据模型、范围或约束变化时，应先更新规格，再继续代码。规格不是开工仪式，而是人和 Agent 共享的当前事实。

规格得到确认后，进入 [Plan](./plan.md) 阶段。
