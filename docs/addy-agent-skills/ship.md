# Ship：安全发布

Ship 不是执行一次部署命令，而是让变更可以追踪、自动验证、渐进暴露、及时观测并快速回滚。

## `git-workflow-and-versioning`

推荐 Trunk-Based Development 与短生命周期分支。每个提交应当：

- 原子化，只表达一个逻辑变化。
- 保持项目可构建、可测试。
- 使用描述原因和结果的提交信息。
- 不混入无关格式化或重构。
- 作为可恢复的 Save Point。

版本发布以标签为事实来源，遵循语义化版本，并维护面向人的 Changelog。

## `ci-cd-and-automation`

CI 把本地质量门槛放到每次推送：

```text
安装 -> 格式/Lint -> 类型检查 -> 单元/集成测试 -> 构建 -> E2E -> Artifact
```

流水线应尽快反馈，把廉价且高概率失败的检查放在前面。失败输出要能回到 Agent，指出具体测试和错误，而不是只留下“CI failed”。

部署策略包括 Preview Deployment、Feature Flag、分阶段发布和明确回滚方案。

## `observability-and-instrumentation`

可观测性与实现并行，不是上线后的补丁。先定义“正常工作”的含义，再为问题选择信号：

- Logs 回答某次事件发生了什么。
- Metrics 显示系统状态与趋势。
- Traces 解释请求如何跨服务流动。
- Alerts 针对用户可感知症状，而不是每个内部波动。

结构化日志避免记录秘密，并携带可关联请求的标识。遥测本身也必须验证，不能只确认代码里调用了日志函数。

## `documentation-and-adrs`

文档解释为什么，而不是复述代码做什么。适合写 ADR 的是难逆、具有真实权衡且未来读者需要背景的决定。

API 文档应贴近类型或 OpenAPI 合同；README 提供快速开始、命令、架构入口和贡献方式。对 Agent 重要的项目命令、边界和模式应进入规则文件。

## `deprecation-and-migration`

旧代码是持续成本。迁移通常遵循：

1. 先构建并验证替代方案。
2. 公告弃用并提供迁移指南。
3. 逐步迁移调用者，监控使用情况。
4. 在明确条件满足后删除旧系统。

根据控制力选择强制弃用或建议弃用；大型替换可使用 Strangler、Adapter 或 Feature Flag 渐进迁移。只标记不删除会产生 Zombie Code。

## `shipping-and-launch`

上线前检查代码质量、安全、性能、可访问性、基础设施和文档。高风险发布采用渐进流量：

```text
内部用户 -> 小比例真实流量 -> 扩大比例 -> 全量
```

每一步都要有观察窗口、继续条件和回滚阈值。

### 回滚计划至少包含

- 触发回滚的指标与症状。
- 明确、已演练的操作步骤。
- 数据库变化如何兼容旧版本。
- 预计恢复时间和负责人。
- 回滚后的验证方式。

## 发布完成标准

发布成功不等于部署任务显示绿色。还需要：

```text
[ ] 真实生产路径已验证
[ ] 错误率、延迟和关键业务指标正常
[ ] 日志、指标、Trace 和告警可用
[ ] Feature Flag 有后续清理负责人
[ ] 回滚路径仍然有效
[ ] 文档、ADR、版本与 Changelog 已更新
```

至此，Addy Agent Skills 的生命周期闭环完成：从显式假设开始，以生产证据结束。
