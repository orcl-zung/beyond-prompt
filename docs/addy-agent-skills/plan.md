# Plan：拆成可验证任务

`planning-and-task-breakdown` 将已确认的规格变成可执行计划。它关注依赖关系、纵向切片、任务大小和阶段性检查点。

## 从依赖图开始

不要直接按照文档出现顺序列 Todo。先识别：

- 哪些能力必须先存在。
- 哪些任务可以并行。
- 哪些外部依赖可能阻塞。
- 哪些风险应该最早验证。

```text
认证基础
  ├─ 登录 API -> 登录 UI
  └─ 会话验证 -> 受保护页面

审计日志（可并行）
```

实现顺序由依赖与风险决定，而不是由功能看起来有多重要决定。

## 优先纵向切片

每个任务应交付一条窄而完整的行为路径：

```text
不推荐：数据库 -> 后端 -> 前端 -> 最后测试

推荐：
任务 1：用户可以创建最小项目
任务 2：用户可以修改项目名称
任务 3：用户可以归档项目
```

纵向切片能更早暴露层间问题，也让每一步都可演示、可回滚。

## 任务模板

```md
## Task 3: 用户可以归档项目

**Depends on:** Task 1

**Outcome:**
用户可以从项目菜单归档项目，归档后默认列表不再显示它。

**Acceptance criteria:**
- [ ] 只有具备权限的用户可归档
- [ ] 成功后列表立即更新
- [ ] 失败时保留原状态并显示错误

**Verify:**
- 运行相关测试
- 在浏览器中执行归档流程
```

任务描述重点是结果与证据。文件列表可以作为当前计划提示，但不应取代行为目标。

## 控制任务大小

理想任务能在一次专注会话完成，并触及有限文件。如果一个任务包含多个“以及”，通常需要继续切分。

太小也会失去价值。只创建类型、只加空函数、只铺数据库而不能观察行为的任务，往往是横向切片。

## 设置 Checkpoint

每个阶段结束时设置检查点：

- 构建和测试是否通过。
- 当前能力能否运行验证。
- 后续假设是否仍然成立。
- 是否需要用户确认再继续。

计划的价值不是预测全部细节，而是让偏差尽早显现，并提供重新规划的位置。

## 并行的边界

只有没有共享未定接口、没有文件冲突、也不依赖同一隐含状态的任务才适合并行。计划中应显式写出并行机会，而不是让多个 Agent 同时碰运气。

计划确认后，进入 [Build](./build.md) 阶段逐片实现。
